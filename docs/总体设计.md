## 前置说明（更详细）

本节对架构边界、组件交互、数据流与典型业务序列做更具体的说明，便于按照模块化设计由 AI 生成代码和图形化文档。

- 架构边界：系统由飞书前端 H5（运行在飞书工作台）、后端 API 层与外部 Bitable 存储三部分组成。前端仅承担展示与操作入口，所有权限校验以后端为准。后端作为业务网关，负责整合 Feishu OAuth、JSAPI 验证、Bitable CRUD 与业务事务控制。
- 数据一致性：采用基于事务幂等 key 的写入策略。所有出入库操作必须写入 `transactions`，并在成功后原子性更新 `inventory`（或通过补偿事务回滚）。
- 可替换性：BYTableClient 需支持两种模式（真实 Bitable API 与内存/Mock 模式），便于 AI 在本地生成可运行 demo。

## 目标
- 快速构建可在飞书工作台运行的 H5 应用，支持搜索、详情、入库、出库等核心流程。  
- 使用 Bitable 作为轻量数据存储与审计流水表。  
- 后端采用 FastAPI，前端采用 React + Vite（移动优先 H5）。

## 主要架构组件
- 前端：React + Vite，移动优先页面（搜索、详情、入库、出库）。集成飞书 JSAPI（lark-samples）。
- 后端：Python 3.10+，FastAPI，uvicorn。提供 8 个左右的 MVP API。封装 Bitable CRUD 客户端。角色鉴权中间件（ADMIN / KEEPER / USER）。
- 数据：Bitable 五表（categories, locations, materials, inventory, transactions）。
- 集成：飞书开放平台（App ID/Secret）、Bitable API、lark-samples 免登/JSAPI。
- 部署：生产需 HTTPS + 域名；可用 Nginx/Caddy 作反向代理，或云托管（Azure/AWS/GCP/飞书云）。

## 功能分解（高层）
- 身份与权限：免登绑定、角色映射、群组管理。  
- 物料检索：按关键字/分类/库位检索，带分页。  
- 物料详情：显示库存、流水历史。  
- 出库：创建出库流水（只允许 KEEPER/ADMIN），更新 inventory。  
- 入库：创建入库流水（允许 KEEPER/ADMIN），更新 inventory。  
- 审计与日志：所有交易写入 transactions 表并保留不可变记录。

## 数据模型（概要）
- categories: id, name, parent_id  
- locations: id, name, code  
- materials: id, code, name, category_id, unit, default_location  
- inventory: material_id, location_id, quantity, last_updated  
- transactions: id, material_id, location_id, type(in/out), qty, operator, timestamp, note

## API 概览（示例）
- GET /me — 返回当前用户与角色
- GET /materials/search?q=&page=&size= — 搜索物料
- GET /materials/{id} — 物料详情（含库存）
- GET /materials/{id}/transactions — 物料流水
- POST /outbound — 提交出库请求
- POST /inbound — 提交入库请求
- GET /inventory — 查询库存（按条件）
- POST /admin/bulk-sync — 管理员批量同步 Bitable 数据

## 非功能需求
- 安全：HTTPS、环境变量存储 Secret、最小权限原则、接口速率限制（可选）。
- 可用性：API 需支持重试与幂等（事务写入需幂等 key）。
- 可维护性：模块化、单元测试覆盖主要逻辑、清晰的接口契约。

## 部署建议
- 本地联调使用隧道（ngrok/Cloudflare Tunnel），上线使用正式域名并配置 SSL。  
- 使用容器化（Docker）或直接部署到云，CI/CD 简单脚本：build image → run migrations → deploy。

## 组件职责与详细行为

- 前端（飞书 H5）
	- 负责展示与交互流程：登录/免登、搜索、详情、入库、出库。所有用户操作产生的表单提交均调用后端 API。前端应尽量在 UI 层做校验（必填、数值范围），但最终权限与校验以后端为准。
	- 负责调用飞书 JSAPI（免登、签名、跳转）并处理平台回调，支持在 `src/api/config` 中切换 mock/real 模式。
	- 页面设计为移动优先，组件应无状态或最小状态，复杂状态交由上层 store（例如 React Context 或轻量状态管理）维护。

- 后端（API 网关 / 业务服务）
	- 入口：接收前端请求，统一做鉴权、限流、请求日志与错误计数。核心职责包括用户映射、权限校验、业务幂等、事务写入、与 Bitable 的同步。
	- 鉴权：对接飞书免登 token，解析用户信息并根据群组/配置映射角色（ADMIN/KEEPER/USER）。每次请求记录 operator metadata（user_id, role, request_id）。
	- 幂等与事务：对于出入库操作要求客户端传递 `idempotency_key`；后端应在短期内缓存该 key 的执行结果以避免重复写入。写入流程先写入 `transactions`（可先预写、补充后再 commit），再原子性更新 `inventory`，异常则产生补偿记录。
	- 错误分类：可重试错误（网络、5xx）与不可重试错误（参数、权限、幂等冲突）明确定义，返回统一错误码与 human-friendly message。

- Bitable（数据层）
	- 作为项目的主数据存储（五表），保证行级记录可查询与追加不可变流水。BYTableClient 封装需支持批量与分页查询，支持事务重试与幂等处理策略。

- 可扩展组件：
	- `后台任务（Worker）`：处理延迟同步、报表生成与外部系统对接（可选，用 Celery/RQ 或云函数实现）。
	- `监控与告警`：采集关键指标（API QPS、错误率、出入库失败率、Bitable 调用失败率），并在阈值触发告警。

## 典型业务序列（出库操作）

1. 前端展示物料，用户选择物料、数量并点击“出库”。前端生成 `idempotency_key`。  
2. 前端调用 `POST /outbound`，请求体包含 `material_id, location_id, qty, idempotency_key, note`。  
3. 后端 `get_current_user` 验证用户并检查角色（需为 KEEPER 或 ADMIN）。  
4. 后端幂等检查：若相同 `idempotency_key` 已成功处理，直接返回先前结果；否则继续。  
5. 后端写入 `transactions`（状态：PENDING），调用 BYTableClient 更新 `inventory`（原子操作或补偿机制）。  
6. 成功后更新 `transactions` 为 COMPLETED，并返回 200 + transaction_id；若失败则写入失败日志并返回明确错误码。

## API 合约规范（简约）

- 所有响应均返回统一 envelope：{"code": int, "message": str, "data": object}。  
- 成功：`code = 0`；业务错误 `code > 0`（例如 1001=参数错误，2001=权限不足，3001=幂等冲突，5001=外部依赖失败）。  
- 时间戳统一使用 ISO8601（UTC）。  

## 错误与重试策略

- 客户端：对 5xx 错误与网络错误做指数退避重试（最多 3 次），对 4xx 错误立即暴露给用户。  
- 服务端：对 Bitable 5xx 做重试（限 3 次，带抖动）；长时间失败则将事务标记为 ERROR 并入告警队列。

## 观察与监控

- 指标：API 延迟、错误率、Bitable 调用成功率、出入库失败率、幂等冲突次数。  
- 日志：结构化日志（JSON）包含 request_id、user_id、role、endpoint、latency、status_code。  
- 报警阈值示例：5 分钟内错误率 > 5% 或 Bitable 调用失败率 > 10% 触发告警。

## 部署与 CI/CD 建议

- CI：后端运行 `pytest`，并做静态类型检查（mypy）与 lint（ruff/flake8），前端运行 `npm run build` 与基本集成测试。  
- CD：构建容器镜像并推送 registry，部署到容器服务或云主机，部署前运行健康检查脚本并回滚策略。

## 测试策略补充

- 单元测试覆盖：BYTableClient 行为、入/出库幂等逻辑、权限校验。  
- 集成测试：用 Bitable Mock 或本地内存模式做端到端流程测试（搜索→详情→出库）。  
- 性能测试：模拟并发出库请求以评估并发写入对 inventory 更新的一致性影响。
