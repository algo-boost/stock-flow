## 一、案例背景：我们要解决什么问题？

机器人研发实验室需要管理分散在货柜、货架、专用架上的硬件物料（电机、传感器、算力板、线缆等）。现状痛点：

- 找物料靠个人记忆，效率低
- 领用、入库缺少标准记录，难以追溯
- 快递到货后暂存与正式上架流程不清晰
- 库存数量靠人工记账，易出错

**团队特征**：小团队、专人维护、低访问量（每天几十笔操作以内），已在飞书协作。

**产品目标（一句话）**：记清楚、找得到、可追溯 —— 不是做 ERP，不是高并发 WMS。

## 三、对话演进全记录（决策是如何一步步形成的）

### 阶段 1：方案是否合适？怎么实现？

**提问**：参照 Wiki 初稿做系统，是否合适？具体怎么实现？

**AI 动作**：阅读 Wiki 原文与分类附图；评估「Bitable + 飞书应用」与团队场景的匹配度。

**结论**：对实验室小团队 **合适**；MVP 做搜索、出入库、库存、流水；暂不做高并发、审批流、独立数据库。

**初版技术倾向**：飞书官方库存模板 + 多维表格「应用模式」（零代码最快）。

---

### 阶段 2：场景澄清 —— 低访问量、专人维护

**用户补充**：没有大量访问，专人维护，不需要很复杂。

| 原考虑 | 调整后 |
|--------|--------|
| Redis 缓存 | 不需要 |
| 乐观锁防超卖 | 不需要 |
| 复杂审批 | 不需要 |
| 自研全栈 | 可大幅简化 |

**沉淀原则**：够用就好；80% 价值在「搜 + 出库 + 入库」。

---

### 阶段 3：调研成熟方案 —— 能否直接拿来用？

| 方案 | 结论 |
|------|------|
| 飞书官方模板 + 应用模式 | 最省事，但无独立 H5 |
| Erniu 开源 | 唯一 Bitable+出入库成品，机器人/卡片形态 |
| lark-samples | 官方网页应用脚手架（免登+JSAPI） |
| Teable / InvenTree / 若依WMS | 成熟但偏离飞书 Bitable 生态 |

**关键发现**：不存在「Bitable + 工作台 H5 + 实验室物料 + 三角色」的开箱即用单一开源项目。

### 阶段 5：权限管理专题设计

### 阶段 8：MVP 技术路线明确

**用户明确**：MVP = 多维表格作数据库 + 飞书网页应用嵌入工作台。

## 四、最终技术架构（截至 2026-06-10）

飞书工作台 → 网页应用（React H5）→ FastAPI → 飞书多维表格（五表）

**五表模型**：categories、locations、materials、inventory、transactions

**MVP API（8 个）**：/auth/feishu/callback、/auth/jsapi-config、/me、/materials/search、/materials/{id}、/materials/{id}/transactions、POST /inbound、POST /outbound
