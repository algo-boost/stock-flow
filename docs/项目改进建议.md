# 物料出入库管理系统 — 项目改进建议

> **文档状态**：v1.0  
> **整理日期**：2026-06-15  
> **整理范围**：只读审查 `docs/`、`backend/`、`frontend/`、测试与配置示例  
> **依据文档**：[产品设计文档](./产品设计文档.md)、[架构设计文档](./架构设计文档.md)、[开发过程实录](./开发过程实录-飞书同步稿.md)、[环境需求](./环境需求.md)  
> **原则**：不扩大 MVP 技术路线；不引入独立数据库、Redis、复杂后台或 ERP 能力；优先补齐「记清楚、找得到、可追溯」。

---

## 1. 总体结论

当前项目已经具备 MVP 主体能力：

- 后端：FastAPI、飞书免登、群组角色、Bitable real/mock 模式、出入库接口、健康检查。
- 前端：React H5 四页（搜索、出库、入库、详情）、飞书 H5 鉴权、角色显隐、移动端表单。
- 数据：五表模型按 Bitable 作为唯一数据源落地，已支持真实物料读写。
- 部署：已形成云主机 + Nginx + ngrok 的临时 HTTPS 路线，`/api/health` 已能证明后端 real 模式可用。

主要改进方向不是推翻架构，而是补齐以下四类缺口：

| 类别 | 主要问题 | 优先级 |
|------|----------|--------|
| MVP 验收闭环 | 飞书工作台端到端仍未完成；搜索页未直接展示库存/库位；快递暂存上架未闭环 | P0 |
| 数据一致性 | 出入库先改库存再写流水，失败时可能出现库存变更无流水；幂等与 session 仅内存 | P1 |
| 文档一致性 | API 数量、部署方式、权限 scopes、日程与已实现状态不一致 | P0 |
| 可维护性与体验 | real 模式测试不足、全表拉取性能、流水正负展示、部署手册分散 | P1/P2 |

## 2. P0：优先处理，直接影响 MVP 验收

### 2.1 完成飞书工作台端到端 UAT

**现状**

开发过程实录记录：服务器 `GET /api/health` 已返回 real 模式正常，但 `GET /` 仍出现 Nginx 静态页 500，阻塞飞书工作台打开 H5。

相关位置：

- `docs/开发过程实录-飞书同步稿.md`
- `docs/环境需求.md`
- `README.md`

**风险**

产品设计文档 §11.2 的验收项包括「飞书工作台内可打开网页应用并完成免登」。只要 H5 静态页未 200，后端再正常也无法完成验收。

**建议**

1. 先将 `frontend/dist` 放到 Nginx 常规静态目录（如 `/var/www/stock-flow`），避免 `/home/stock` 目录权限或 SELinux 导致 500。
2. 固化部署口径：AutoDL/平台 UI 占 80 时，stock-flow 使用 8080，ngrok 指向 8080。
3. 在 `docs/环境需求.md` 或新增 `docs/部署指南.md` 中写清楚最终验证命令：

```bash
curl -sI http://127.0.0.1:8080/
curl -s http://127.0.0.1:8080/api/health
```

**验收**

- `GET /` 返回 200。
- ngrok HTTPS 页面显示 H5，不再出现 AutoDL Flow 登录页。
- 飞书工作台内完成免登、搜索、出库、入库。

### 2.2 搜索结果应直接展示库存与库位

**现状**

PRD §2.5、§4.2、§11.2 多次强调「搜索后看到库位与库存数」。当前 `frontend/src/pages/Search.tsx` 使用 `GET /materials/search`，结果类型是 `Material`，页面只展示名称、编码、分类、单位，不显示库存分布。

相关位置：

- `frontend/src/pages/Search.tsx`
- `backend/app/api/materials.py`
- `backend/app/models.py`
- `docs/产品设计文档.md`

**风险**

用户最高频场景 S1 是「搜索 → 看到位置和库存 → 出库」。如果搜索页只显示物料卡片，用户必须点详情才能知道有没有库存，流程变慢，不符合「找得到」目标。

**建议**

两种做法任选其一：

1. 让首页搜索改用 `GET /materials/catalog?q=...&stock_only=false`，直接拿 `MaterialDetail`，显示总库存和库位摘要。
2. 保留 `GET /materials/search`，但将返回模型扩展为带 `total_quantity`、`locations_summary` 的轻量搜索结果。

**验收**

- 搜索「大喵」后，卡片中可见总库存、至少一个库位名称。
- 无库存物料有明确提示，而不是只显示主数据。

### 2.3 文档 API 清单需要和实现同步

**现状**

权威文档仍反复写「8 个 MVP API」，但实现已经包括更多实际必需接口：

| 已实现接口 | 用途 | 当前文档状态 |
|------------|------|--------------|
| `POST /auth/feishu/login` | H5 免登主路径 | README 有，架构 8 API 未列 |
| `GET /materials/catalog` | 出入库页一次拉取物料+库存 | 开发实录有，PRD/架构未正式列 |
| `GET /locations` | 入库页库位选择 | README 未列入主要 API |
| `GET /inventory` | 库存查询 | README 有，架构 8 API 未列 |
| `GET /health` | 部署与依赖诊断 | README 提到但 API 表不完整 |
| `POST /admin/bulk-sync` | 管理员快照诊断 | README 有，架构定位不清 |

相关位置：

- `docs/产品设计文档.md`
- `docs/架构设计文档.md`
- `README.md`
- `backend/app/api/*.py`

**风险**

验收、开发日程和 README 口径不一致，会导致后续开发者不知道哪些接口是 MVP 必需、哪些是联调辅助。

**建议**

更新权威文档中的 API 表，分为：

- MVP 用户接口：`/me`、`/materials/search`、`/materials/catalog`、`/materials/{id}`、`/materials/{id}/transactions`、`/locations`、`/inbound`、`/outbound`
- 飞书鉴权接口：`/auth/jsapi-config`、`/auth/feishu/login`、`/auth/feishu/callback`
- 运维/管理接口：`/health`、`/inventory`、`/admin/bulk-sync`

同时在变更记录中标注：代码已从「固定 8 API」演进为「核心 API + 鉴权/运维 API」。

### 2.4 部署文档需要吸收 8080 + ngrok 的真实路径

**现状**

`docs/环境需求.md` 和 `README.md` 主要写本地 Vite + ngrok 或传统 HTTPS 域名；开发过程实录记录了真实服务器环境：AutoDL Flow 占 80、Nginx 改 8080、ngrok 指向 8080、`/api/health` 已通。

**风险**

后续复现部署时容易继续误用 80 端口，打开 AutoDL Flow 登录页。

**建议**

新增或更新部署章节：

```text
飞书 / 浏览器
  → ngrok HTTPS
  → 127.0.0.1:8080 Nginx
  → /api 反代 127.0.0.1:8000
  → / 静态文件 /var/www/stock-flow
```

并明确：

- 不对 ngrok 域名跑 certbot。
- 无自有域名时，飞书三处 URL 填当前 ngrok HTTPS 域名。
- `backend/.env` 的 `FEISHU_REDIRECT_URI`、`CORS_ORIGINS` 与飞书开放平台同步。
- 如果服务器有 `http_proxy`，先处理 ngrok `ERR_NGROK_9009`。

## 3. P1：数据可靠性与安全性改进

### 3.1 出入库写入顺序存在一致性风险

**现状**

`backend/app/bitable/repository.py` 的 `apply_inbound` / `apply_outbound` 先更新 `inventory`，再写 `transactions`。

当前流程：

```text
校验物料/库存
→ update/create inventory
→ create transaction
→ 返回 transaction_id
```

**风险**

如果 `inventory` 已更新，但写 `transactions` 时 Bitable API 失败，会出现库存已变化但无流水，违背 PRD 的「谁什么时候动过」和「流水只追加」原则。

**建议**

按 MVP 保守方案处理，不引入复杂事务系统：

1. 增加失败补偿：写流水失败时尝试把库存回滚到原值，并记录日志。
2. 或调整为先写流水（带状态/备注），再更新库存；若库存更新失败，再追加一条失败/冲正备注。
3. 至少在文档中明确当前风险和人工修复流程。

**验收**

- 模拟写流水失败，不会静默留下「有库存变化、无流水」。
- 后端日志能定位 material、location、qty、operator。

### 3.2 幂等缓存仅在内存中

**现状**

`backend/app/utils/idempotency.py` 使用模块级 dict 保存幂等结果，TTL 为 24 小时。

**风险**

- 后端重启后幂等记录丢失。
- 如果未来 systemd/uvicorn 开多个 worker，同一请求可能落到不同进程，幂等失效。
- dict 没有容量上限，长期运行会增长。

**建议**

MVP 阶段不必引入 Redis，但应做到以下两点：

1. 部署文档明确 `uvicorn` 单进程运行，避免多 worker。
2. 给幂等缓存加定期清理或容量上限。

后续若出现重复提交问题，再考虑基于 Bitable 新增「幂等键」字段，按业务表查询去重。

### 3.3 Session 仅在内存中，需明确生产约束

**现状**

`backend/app/services/session_store.py` 使用内存 dict 保存登录 token。前端已处理后端重启后 token 失效并自动重新免登。

**风险**

同幂等缓存一样，多 worker 或多实例会造成会话不共享；重启后所有 session 失效。

**建议**

MVP 可以接受，但应在部署文档中明确：

- 单实例、单 worker。
- 重启服务会触发用户重新免登，这是预期行为。
- `FEISHU_ROLE_OVERRIDES` 只能用于联调，生产需移除。

### 3.4 `/health` 暴露信息偏多

**现状**

`GET /health` 返回 Bitable 模式、配置状态、物料数量、IM 权限探测结果。

**风险**

如果长期公网暴露，会泄露系统依赖状态和部分组织配置线索。

**建议**

MVP 联调阶段保留详细 health；正式上线时可拆分：

- `/health`：只返回 `status: ok`
- `/admin/diagnostics`：仅 ADMIN 可访问，返回 Bitable/Feishu 诊断详情

### 3.5 `FEISHU_ROLE_OVERRIDES` 应避免生产误用

**现状**

`backend/app/config.py` 支持 `FEISHU_ROLE_OVERRIDES=ou_xxx:ADMIN`，用于 IM 权限未就绪时兜底。

**风险**

生产环境若误留 override，会绕过飞书群组角色，影响权限可信度。

**建议**

- 文档中标注「仅 dev/uat 可用」。
- 后续代码可在 `APP_ENV=prod` 且存在 override 时拒绝启动或输出强警告。

### 3.6 real 模式缺少启动期配置校验

**现状**

`BITABLE_MODE=real` 时，业务请求会直接创建 `BitableRepository`；如果 `BITABLE_APP_TOKEN` 或表 ID 缺失，通常到实际接口调用时才暴露为 Bitable 读写错误。

相关位置：

- `backend/app/config.py`
- `backend/app/main.py`
- `backend/app/services/inventory.py`

**风险**

部署时容易出现「服务已启动，但业务接口 502」的情况，排查成本高。

**建议**

在 FastAPI lifespan 中做 fail-fast 校验：

- `BITABLE_MODE=real` 时必须具备 app token、materials、inventory、transactions、locations 表 ID。
- `MOCK_AUTH_ENABLED=false` 时必须具备 Feishu App ID/Secret。
- `APP_ENV=prod` 时如果 `MOCK_AUTH_ENABLED=true` 或存在 `FEISHU_ROLE_OVERRIDES`，拒绝启动或至少输出醒目错误日志。

## 4. P1：产品体验改进

### 4.1 飞书 JSAPI 鉴权流程未完整调用 `h5sdk.config`

**现状**

前端 `frontend/src/auth/feishu.ts` 会请求 `/auth/jsapi-config` 获取 `appId`，但没有把后端返回的 `timestamp`、`nonceStr`、`signature` 传入 `h5sdk.config()`；README 中描述的流程是 `h5sdk.config + tt.requestAuthCode`。

相关位置：

- `frontend/src/auth/feishu.ts`
- `backend/app/api/auth_routes.py`
- `README.md`

**风险**

在飞书客户端真实环境里，免登或后续扫码等 JSAPI 能力可能出现不稳定或不可用；后续做扫码时也会再次踩坑。

**建议**

将 JSAPI 初始化拆成明确流程：

1. `GET /auth/jsapi-config?url=<currentUrl>` 获取完整签名参数。
2. 调用 `window.h5sdk.config({ appId, timestamp, nonceStr, signature, jsApiList: [...] })`。
3. 在 `h5sdk.ready` 后再调用 `tt.requestAccess` / `tt.requestAuthCode`。
4. 文档中明确：免登主路径为 `POST /auth/feishu/login`，callback 仅保留为可选调试路径。

### 4.2 详情页流水数量正负显示不准确

**现状**

`frontend/src/pages/Detail.tsx` 中流水数量显示逻辑是：只要 `quantity > 0` 就加 `+`。但当前 Bitable 写入出库数量也是正数，只靠 `type` 区分入库/出库。

**风险**

出库流水会显示为 `+1`，虽然左侧 badge 是「出库」，但数字含义容易误导。

**建议**

前端显示时按 `tx.type` 判断符号：

- 入库：`+qty`
- 出库：`-qty`

或后端统一返回展示用字段 `signed_quantity`。

### 4.3 入库页大批量物料时选择体验会变差

**现状**

`frontend/src/pages/Inbound.tsx` 一次加载全部 catalog 和全部 locations，并使用 Selector 展示。

**风险**

物料几十条时可用；超过百条后，移动端选择器会很长。

**建议**

短期：在入库页增加搜索筛选。  
中期：物料选择改为搜索框 + 列表，复用出库页 `catalog` 列表模式。

### 4.4 搜索分页能力未在前端暴露

**现状**

后端 `GET /materials/search` 支持 `page`、`size`，前端 `SearchPage` 固定调用默认第一页 20 条，没有加载更多。

**风险**

物料数量增加后，搜索空关键词或宽泛关键词只能看到前 20 条。

**建议**

MVP 可先保留，但如果要支持「浏览全部」，应增加「加载更多」或改用 `catalog`。

### 4.5 飞书扫码能力尚未实现

**现状**

PRD 在交互要点中提到扫码，但阶段划分里也将扫码列为 P2。当前代码只实现飞书免登和 JSAPI config，未调用扫码 API。

**建议**

不阻塞当前 MVP；在文档中统一口径：扫码作为 P2，不再标 P1 必需，避免验收争议。

### 4.6 快递暂存上架流程未闭环

**现状**

系统已有「快递暂存区」库位概念，入库可选择暂存区；但「暂存区 → 正式库位」调拨动作未实现。

**风险**

PRD §11.2 把「快递到货能先落暂存区，再上架到正式库位」列入 MVP 验收，但当前功能只支持通过一次出库 + 一次入库模拟调拨。

**建议**

二选一：

1. 如果坚持 MVP 验收包含暂存上架：增加 `transfer` 业务能力，写两条流水或一种调拨流水。
2. 如果暂存上架延后：把 PRD 验收项改为 P2，并在 MVP 中说明「临时用出库+入库处理」。

## 6. P2：可维护性与性能优化

### 6.1 Bitable 全表拉取后内存过滤

**现状**

`BitableRepository` 多处使用 `_list_all` 拉全表，再在 Python 内存中过滤、分页。

同时，`InventoryService` 由路由依赖每次创建，进而每次创建新的 `BitableRepository` 和 `BYTableClient`；仓储内的 `_materials_cache`、`_locations_cache` 与 token 缓存很难跨请求复用。

**风险**

当前只有少量物料没有问题；如果物料、库存、流水增长到几百/几千条，H5 出库页和详情页会变慢。

**建议**

按数据增长阶段优化：

| 数据量 | 建议 |
|--------|------|
| < 200 物料 | 保持当前实现 |
| 200～1000 物料 | `catalog` 增加关键字服务端过滤，减少前端一次性渲染 |
| > 1000 物料 | 使用 Bitable filter / view / search 能力，按页拉取 |

另外可将 `BitableRepository` 或 `BYTableClient` 提升为进程级共享对象，让短期缓存真正生效；仍需注意写入后主动失效库存相关缓存。

### 6.2 `list_inventory` real 模式重复读取库存

**现状**

`repository.py` 的 `list_inventory` 遍历每个 material，再调用 `get_inventory_for_material`；后者会重新加载库存记录，存在重复读取。

**建议**

后续改为一次加载 `inventory_map`、`inventory_records`、`locations` 后统一组装。

### 6.3 Bitable token 缓存粒度较低

**现状**

`BYTableClient` 实例级缓存 `tenant_access_token`，但 `InventoryService` 每次依赖注入都会创建新的 `BitableRepository` 和 `BYTableClient`。

**风险**

高频请求时可能重复获取 token。低访问量下影响不大。

**建议**

后续将 token 缓存提升为进程级或封装共享 client。

### 6.4 前端缺少测试

**现状**

前端 `package.json` 只有 `dev/build/preview`，没有测试脚本。

**建议**

MVP 可先不加完整测试框架，但至少增加：

- `npm run build` 作为必跑检查。
- 后续加入 API client 的 fetch mock 测试。
- 手工 UAT 表单覆盖四页核心流程。

### 6.5 后端 real 模式缺少可重复测试

**现状**

`backend/tests/test_api.py` 使用 mock headers 和 mock store；真实 Bitable 写入主要靠人工验证。

**建议**

增加不默认执行的 real 冒烟测试脚本，使用专门测试表或 dry-run：

- 检查五个 table id 是否可读。
- 检查 link/user 字段解析。
- 可选：对测试物料执行一次入库 + 出库回滚。

## 7. 可以保留的设计

以下做法符合项目定位，不建议为了“更像企业系统”而过度改造：

| 设计 | 保留理由 |
|------|----------|
| Bitable 作为唯一数据源 | 符合小团队、低访问量、专人维护 |
| 不引入 MySQL/Redis | 当前复杂度不需要 |
| 主数据维护走 Bitable | 避免自研后台，库管可直接维护 |
| H5 四页 | 已覆盖搜索、出库、入库、详情 |
| USER 可出库、不可入库 | 与 PRD 权限矩阵一致 |
| 出库用途必填 | 已在前后端校验，利于追溯 |
| 健康检查详细输出 | 联调阶段非常有价值，上线后再收敛 |
| 8080 + ngrok | 无域名、80 被占用时的现实可行方案 |

## 8. 建议实施顺序

### 第一轮：验收闭环

1. 修复 Nginx 静态页 500。
2. 完成 ngrok 8080 + 飞书三处 URL 同步。
3. 飞书工作台内做一次完整 UAT。
4. 搜索页显示库存/库位。
5. 同步 PRD/架构/README 的 API 与部署口径。

### 第二轮：数据可靠性

1. 出入库写入失败补偿或风险日志。
2. 明确单 worker 部署约束。
3. 限制或标注生产环境禁用 `FEISHU_ROLE_OVERRIDES`。
4. 调整详情页流水正负显示。

### 第三轮：体验与扩展

1. 入库页物料搜索。
2. 快递暂存上架/调拨能力。
3. JSAPI 扫码。
4. 低库存提示。
5. Bitable 查询性能优化。
