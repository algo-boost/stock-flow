## 一、案例背景：我们要解决什么问题？

机器人研发实验室需要管理分散在货柜、货架、专用架上的硬件物料（电机、传感器、算力板、线缆等）。现状痛点：

- 找物料靠个人记忆，效率低
- 领用、入库缺少标准记录，难以追溯
- 快递到货后暂存与正式上架流程不清晰
- 库存数量靠人工记账，易出错

**团队特征**：小团队、专人维护、低访问量（每天几十笔操作以内），已在飞书协作。

**产品目标（一句话）**：记清楚、找得到、可追溯 —— 不是做 ERP，不是高并发 WMS。

### 阶段 15：HTTPS 与 ngrok 方案澄清（2026-06-12）

**提问**：没有域名，飞书要求 HTTPS，怎么配？

**结论**：

| 方案 | 决策 |
|------|------|
| 购买域名 + certbot | ❌ 暂不采用 |
| 服务器本机 ngrok 穿透 | ✅ 采用：`ngrok http <端口>` 得 `https://xxxx.ngrok-free.dev` |
| 飞书三处 URL | 主页、重定向 URL、H5 可信域名 **必须一致** |
| `backend/.env` | `FEISHU_REDIRECT_URI`、`CORS_ORIGINS` 同步 ngrok 域名 |

**ngrok 额外踩坑**：

- 服务器存在 `http_proxy` 等环境变量 → 免费 ngrok 报 **ERR_NGROK_9009**；需 `unset http_proxy https_proxy ...` 并检查 `~/.config/ngrok/ngrok.yml` 无 `proxy_url`
- 从 AWS S3 下载 ngrok 包失败（非 gzip）→ 可改用 `npm install -g ngrok` 或从本机 scp 安装包

**备选**：若 ngrok 持续受代理限制，可换 **cloudflared** 隧道。

### 阶段 16：AutoDL Flow 占 80 端口 —— 打开应用却是登录页（2026-06-12）

**现象**：启动/访问应用时出现 **「AutoDL Flow 登录界面」**；ngrok 日志出现 `GET /login`。

**排查过程**：

```bash
sudo ss -tlnp | grep -E ':80|:8080'
curl -I http://127.0.0.1:80
# → HTTP/1.1 302 FOUND, Location: /login

curl -s http://127.0.0.1/login | head -5
# → 中文 HTML 登录页（AutoDL Flow，非 stock-flow）
```

**根因**：

- 80 端口虽由 **Nginx** 监听，但 **default 站点仍是 AutoDL Flow**（302 → `/login`），不是 `stock-flow.conf`
- stock-flow **没有** `GET /login` 路由；飞书登录走 `POST /api/auth/feishu/login`
- 用户访问公网 IP 或 `ngrok http 80` 时，实际打开的是 AutoDL 平台 UI

**决策**：**不抢 AutoDL 的 80**，stock-flow 改监听 **8080**，ngrok 指向 8080。

## 九、2026-06-15：试用反馈驱动的功能补强、性能优化与数据安全讨论

### 9.1 本轮背景

2026-06-15 的开发重点来自真实试用反馈：系统主体功能已能跑通，但在实际使用时暴露出若干 MVP 验收前必须补齐的问题。

用户连续提出的核心问题包括：

1. 入库时只能选择已存在物料，无法处理数据表中没有的新物料。
2. 希望在未接入飞书的情况下本地测试功能。
3. Bitable 表格首次拉取耗时较大，出入库页面多次操作后仍可能重新拉表。
4. 登录过期时间偏短，重复打开应用时确认账号耗时较长。
5. 手动刷新缓存时出现 500，启动预热遇到 `Data not ready` 后反复失败。
6. 真实仓库流程需要支持“库内物品移动”，例如快递暂存区上架到正式库位。
7. 数据量增长到上万条后，搜索、入库、出库、移动页面不能一次性拉取全量数据。
8. 需要提前考虑数据是否会丢失、如何防止、如何备份。

本轮处理原则保持不变：**不推翻 MVP 技术路线，不引入独立数据库、Redis、复杂后台或 ERP 能力；继续以 Bitable + 飞书 H5 + FastAPI 薄层为主。**

### 9.2 新物料入库问题：入库页快捷新增物料

### 9.4 Bitable 拉取慢：缓存、写穿透与刷新机制

#### 问题

试用中发现 Bitable 多维表格首次读取耗时很大；更严重的是，多次出入库后仍可能重新拉表，导致用户体感卡顿。

#### 原因分析

主要原因不是单个页面慢，而是访问路径中存在多次整表读取：

1. 出库/入库页需要物料表、库存表、库位表等多表数据。
2. real 模式下 Bitable API 读取整表分页，本身延迟较高。
3. 旧逻辑在写库存后直接失效缓存，下一次读又变成冷加载。
4. 多个页面同时请求同一张表时，可能并发重复拉取。

#### 优化策略

本轮采用了“保留 Bitable 唯一数据源 + FastAPI 进程内缓存”的轻量方案。

| 优化项 | 说明 |
|--------|------|
| 表级缓存 TTL | Bitable 表读取结果放入进程内 `_TABLE_CACHE` |
| in-flight 去重 | 同一张表正在拉取时，后续请求等待同一个任务 |
| 启动预热 | 服务启动时可预热五表，降低首个用户等待 |
| 写穿透缓存 | 出入库成功后更新缓存记录，而不是直接整表失效 |
| 手动刷新缓存 | KEEPER / ADMIN 可点击刷新按钮同步 Bitable 手工改动 |
| best-effort 刷新 | 某张表刷新失败时保留旧缓存，不导致整个接口 500 |
| 启动预热失败不阻塞 | `Data not ready` 时记录 warning，首次请求再按需读取 |

#### 本轮修复的典型错误

启动或刷新时曾出现：

```text
RuntimeError: 读取表 tblNudpsXTrOGo2o 失败: Data not ready, please try again later
```

处理方式：

- 启动预热不再反复重试。
- 刷新缓存改为逐表 best-effort。
- 刷新失败的表保留旧缓存。
- 前端刷新按钮对“部分失败”给出提示，而不是直接报服务器内部错误。

### 9.5 登录过期与登录速度优化

#### 问题

用户反馈“隔一会就得重登”，且从打开应用到确认账号耗时偏长。

#### 优化方向

| 问题 | 调整 |
|------|------|
| session 过期太快 | 调整 `SESSION_TTL_SECONDS`，默认 1 天 |
| 活跃用户仍被踢出 | 增加 sliding TTL，访问时自动续期 |

| 群组角色判断慢 | 增加角色缓存，并发检查多个群组 |
| 401 后体验差 | 前端 API 层自动触发飞书重新登录并重试原请求 |

对应配置示例已补充到 `backend/.env.example`：

```env
SESSION_TTL_SECONDS=86400
SESSION_SLIDING_TTL=true
FEISHU_ROLE_CACHE_TTL_SECONDS=3600
```

### 9.6 库内移动 / 调拨功能

#### 业务背景

真实仓库中，库存不只会入库和出库，还会发生库内移动：

- 快递到货先放“快递暂存区”，拆包后上架到正式库位。
- 库位整理时，把同一物料从一个货柜移动到另一个货柜。
- 物料归位时，需要从临时库位移动到默认库位。

#### 最终流程

```text
选择物料
  → 选择源库位
  → 选择目标库位
  → 输入数量
  → 填写备注
  → 确认移动
```

后端逻辑：

```text
校验源库位库存 >= 数量
校验源库位 != 目标库位
源库位库存 -N
目标库位库存 +N
写 transactions 流水，类型=移动，数量=-N，备注记录目标库位
```

#### 权限

库内移动属于库存维护行为，仅 `KEEPER / ADMIN` 可操作，`USER` 不可操作。

#### 落地内容

| 层 | 改动 |
|----|------|
| 文档 | PRD 和架构文档增加库内移动/调拨说明 |
| 后端模型 | 新增 `TransferCreate`、`TransferResult` |
| 后端 API | 新增 `POST /transfer` |
| Bitable real | 实现源库位扣减、目标库位增加、移动流水写入 |
| mock 模式 | 支持本地移动测试 |
| 前端 | 新增 `frontend/src/pages/Transfer.tsx` |
| 导航 | 底部 Tab、首页快捷入口、物料详情页入口增加“移动” |
| 测试 | 增加 USER 禁止移动、KEEPER 移动成功、幂等与流水断言 |

#### 一致性处理

Bitable API 没有传统数据库事务，因此本轮采用“失败补偿”策略：

- 如果写目标库位失败，回滚源库位。
- 如果写移动流水失败，回滚源库位和目标库位。
- 移动流水采用单条记录，备注写明“移动至目标库位”，降低两条流水半成功的风险。

### 9.7 搜索结果库存摘要与流水方向优化

#### 搜索结果补强

用户需要“找得到”，所以搜索结果不能只显示物料名称，还应直接看到库存数和库位摘要。

本轮新增 `MaterialSearchItem`：

```text
Material + total_quantity + locations_summary
```

前端搜索卡片显示：

```text
物料名称
编码 / 分类 / 库存 N 个
库位A 3 · 库位B 2
```

#### 流水方向优化

出库流水原先记录正数，阅读时不够直观。本轮改为：

- 入库：`+N`
- 出库：`-N`
- 移动：源库位记录 `-N`，备注标明目标库位

这样物料详情页的最近流水更接近真实台账表达。

### 9.8 大数据量性能优化：默认分页浏览，避免整表渲染

#### 新问题

用户进一步提出：如果库存数据到上万条，现有入库页把全部物料塞进选择器，是否不利于大量数据？

结论：**不利于大量数据。**

原入库页的问题：

1. 首屏需要拉全部物料。
2. 大量 `Selector` 选项在移动端渲染卡顿。
3. 物料多时难以浏览和搜索。
4. 出库/移动页如果依赖整表 `catalog`，数据增长后同样会慢。

#### 决策

将“默认显示全部数据”定义为：

> 默认分页显示第一页，而不是一次性加载上万条。

#### 交互调整

| 页面 | 调整后 |
|------|--------|
| 搜索页 | 打开后默认显示全部物料第一页，支持搜索和加载更多 |
| 入库页 | 默认分页浏览全部物料；选中物料后填写入库单；找不到时快捷新增 |
| 出库页 | 默认分页浏览有库存物料；选中后再查该物料详情库存 |
| 库内移动页 | 默认分页浏览有库存物料；选中后再查该物料详情库存 |

#### 后端接口调整

`GET /materials/search` 成为分页查询主入口，新增参数：

```text
q
page
size
stock_only
```

其中：

- `stock_only=false`：用于搜索页、入库页，浏览全部物料。
- `stock_only=true`：用于出库页、移动页，只浏览有库存物料。

`GET /materials/catalog` 保留为小数据和兼容场景，不再作为出入库/移动页首屏主路径。

### 9.9 数据安全与备份讨论

#### 用户问题

用户提出：

> 存储的数据有没有可能丢失？如何防止？如何备份？

#### 风险判断

Bitable 本身作为云端数据源可靠性较好，但项目仍然存在以下数据风险：

| 风险 | 说明 |
|------|------|
| 人为误删 | 管理员直接删除表、字段或记录 |
| 手工改库存 | 绕过 API 修改 `inventory.quantity`，造成无流水库存 |
| 流水被改 | `transactions` 被删除或修改，审计链断裂 |
| API 半成功 | 库存变了但流水失败，或移动中两端库存不一致 |
| 表结构损坏 | 字段名、字段类型或关联关系被改坏 |
| 无外部备份 | Bitable 内部数据损坏时缺少独立恢复来源 |

#### 防护原则

1. **权限防护**：普通用户只读库存和流水，库管通过 H5 操作，管理员才可维护结构。
2. **业务防护**：库存变化只走 API，`transactions` 只追加，纠错用反向流水。
3. **失败补偿**：写流水失败时尝试回滚库存。
4. **备份防护**：定期导出五表快照，不只依赖同一个 Bitable 空间。

#### 建议备份方案

| 内容 | 频率 | 说明 |
|------|------|------|
| `transactions` | 每小时或每天多次 | 流水最关键，决定能否追溯和重算库存 |
| 五表全量快照 | 每天一次 | categories、locations、materials、inventory、transactions |
| 重大操作前备份 | 手动执行 | 改字段、批量导入、权限调整前 |

推荐格式：

- JSONL：便于程序恢复，保留结构。
- CSV/XLSX：便于人工查看和排查。

推荐保留策略：

- 每日备份保留 30 天。
- 每周备份保留 6 个月。
- 每月备份长期保留。

后续建议新增“库存校验脚本”：定期用 `transactions` 重算理论库存，与 `inventory` 当前库存比对，发现差异后告警。
